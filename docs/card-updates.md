# カード更新の共通経路

2026-09-23 本人指定：新カードだけでなく、進化・限界突破・ヒーロー追加、バランス変更、同一URLの画像差し替えを一度の更新で全体へ反映する。各画面に個別の例外を増やさない。

## 正本と反映先

公開メタデータの正本は `catalogue/cards.json`。日本語内部名・英名・公式ID・slug・コスト・種別・読み・役割・Wiki取得先・形態別画像とSHA256を管理する。手作業の役割・検索別名はAPI更新で上書きしない。

| 利用先 | 経路 |
|---|---|
| ビルダー・検索・人気デッキ・マイページ | 生成済み `js/cards-data.js` の共通関数 |
| 公式ゲームへのコピー・リンク読込 | 台帳内の公式ID。古いdataブランチのID表を別取得しない |
| 試合収集 | `card-catalogue.cjs` からID/slug→内部名・コストを取得 |
| 詳細の取得 | 毎回台帳全件から取得対象を再構成。既存statsに無いカードも追加 |
| カード個別ページ | 同じ台帳・更新候補statsを入力。名称の結合はslugを優先 |
| OGP・ランキング画像・Workerのカード判定 | 配信済み `catalogue/manifest.json` をWorkerが60秒間隔で再確認 |
| 監修シート | 確認済み形態別数値だけ同期。進化行へ通常値を流用しない |

`js/cards-data.js` は生成物。共通関数は `tools/templates/cards-runtime.js` を編集する。旧 `gas/Code.gs` は移行前の参考資料で本番収集の正本ではない。

## 更新と公開

```sh
# 台帳を編集した後。画像の内容を検証して生成（公開操作は含まない）
node tools/update-card-catalogue.js --images
node tools/update-card-catalogue.js --check
node --test tools/test-card-catalogue.mjs
node tools/check-card-images.js --lint-only
```

既存 `build-card-stats.yml` を統合更新経路にした。毎日13:40 JSTに既存CR_TOKENで公式 `/cards` を照合し、既知カードのID・英名・コスト・既知の追加形態を更新。画像全件のPNG構造と内容ハッシュを検査し、R2現物を土台に詳細の候補を作り、個別ページ・17言語・リンクを検査してから公開する。手動 `dry_run=true` はGit/R2/シート更新も通知送信もしない。レビュー用artifactは公開カード台帳と差分報告だけで、生試合・非公開統計を含めない。

未知のカードは日本語名・種別・役割・Wiki取得先を確認して**台帳1か所**へ追加する。APIだけでは確定できない意味を推測して公開しない。未対応のアイコン種別、公式一覧からの消失、対応していない進化段階は更新を止めて差分に残す。新しい仕組みそのものはレンダラーの対応が必要だが、通常カードとして黙って通さない。

画像内容SHA256がURLの版番号になる。画像URLが変わらなくても内容変更でブラウザーとWorkerの生成画像キャッシュが切り替わる。JS共通関数の変更もscriptの版番号に含む。Worker更新は通常のカード追加には不要。初回通信失敗は同梱台帳、更新失敗は最後に検証できた台帳を利用し、`/api/card-catalogue` と `X-Card-Catalogue` / `X-Card-Catalogue-Source` で稼働版を確認できる。

GitHub PagesとR2は別サービスなので同時切替ではない。両方の生成・検査を先に済ませ、ページ反映後にR2を更新する。R2の元データがビルド中に変わっていれば公開を止める。途中失敗はworkflow失敗として残り、同じ経路を再実行する。画像版はPagesのmanifestに追従するため、新カードのたびにWorkerへ辞書を手コピーしない。

## 数値・形態・バランスの正確さ

- 取得元はコミュニティWikiで、公式APIの戦闘能力値ではない。取得成功日とゲーム内調整の確認日は同一視しない。「翌日必ず最新」の表示を廃止した。
- 各カードに `freshness.status=current/stale/missing`、取得確認時刻、最後の成功時刻を記録。失敗時は直近の数値を維持し、全体 `updated` を最新と偽らない。取得候補と失敗を含む鮮度情報は検証して反映し、その後のworkflowを失敗にして要確認箇所を知らせる。
- 通常と形態別の数値を分離。各形態に `wikiPage` が確認できた場合に同じ取得器で取得し、未確認なら `formStats` を未確認と表示。通常数値を進化・ヒーローの値としてコピーしない。
- 差分式の `apply-balance.js` は元JSONのSHA256 (`meta.baseHash`)、発効日、対象カード・形態・全フィールドを確認。未対応項目・一部欠損があれば出力を作らず、適用済み印も付けない。同じパッチは再適用しない。過去の `balanceOutOfScope` は未解消の履歴として残す。通常は日次の現在値再取得を使い、古い比率パッチを再取得後の値へ重ねない。
- 画像が取得できない場合、サイトは同じ形態の代替ホストを一度試し、名前付きの独自確認中画像を表示する。別形態への置換・非表示はしない。ランキング画像は全カードの検証に失敗したら503を返し、不完全な画像を正常キャッシュへ入れない。

## 2026-09-23の確認と残件

123カード、通常123・限界突破42・ヒーロー17の182画像を検証。ガーゴイルジャイアントのWikiページは本文が `Coming soon...` のため詳細数値を取得できない。取得対象には含めて毎日再試行し、未取得と表示する。既存の形態別数値59件は検証済み出典の指定待ちであり、取得済みとは扱わない。Wikiの更新遅延や将来の全く新しい仕組みを自動で正解にできると約束するものではない。

テストは新カードの各利用先への反映、形態追加、同URL画像変更、未知形態の検出、名称変更、失敗時の保持、バランスの部分適用防止を含む。Worker側は更新競合・最後の正常版保持・不正manifest・画像完全性を検証する。

未知カード・未対応の進化段階を含む取得試合は、`private/raw/unmapped-card-battles-v1/part-N/` に元API観測を保存する。250件単位のディスク分割は通信・メモリの単位であり、総保存数の上限ではない。台帳対応前の試合を通常カードへ推測変換しない。保存した未解釈観測の自動再集計はこの更新経路には含まず、新しい仕組みの解釈を確認した後にPRIVATE分析側から再開する。
