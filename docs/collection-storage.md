# 試合収集と保存（2026-09-23）

取得量の制限と、取得済みの試合を使う期間は別々に扱う。帯別集計は直近7日を対象とするが、1帯1,600件／全体80,000件の切り捨ては廃止。

## 保存と再集計

- `tools/event-store.cjs` は汎用のJSONストリーム読取・SQLite保存・重複除去・圧縮転送だけを担う。既存の帯別集計式は変更していない。新規の分析手法を公開側へ追加するものではない。
- 1試合ずつSQLiteへ取り込み、対象期間の全件を1行ずつ既存集計へ渡す。全件をJS配列へ展開しない。
- 作業表には既存集計で使う項目だけを保存する。タグ・形態・レベル等を含む元の全項目は生アーカイブに残る。メモリだけでなく一時ディスクの膨張も抑える。
- 数百万件でも書き込みが偏らないよう、本文を追記順、重複判定キーを別索引に保存する。書き込みログ（WAL）と128MiBのページキャッシュを使い、スナップショットはDBを閉じてログの反映を完了した後に作る。初期形式からの移行は別ファイルへ全件コピーが成功した時だけ置換し、R2の前回保存は維持する。
- 同じ試合を両者から取得した場合は、試合時刻・種別・順序を問わない参加者タグの組で重複を除く。タグなしの旧記録はトロフィー・クラウン・デッキの組で判定する。両者のカード使用はそれぞれ1回として集計する。
- `private/trophy-events-v2.sqlite.gz` が毎回の再開用データ。更新前にR2へ保存できたことを確かめ、その後に帯別表示用JSONを公開する。失敗時に空の集計を上書きしない。
- 生試合は既存の `private/raw/trophy-battle-events-v1/YYYY-MM-DD/run-*.json` に継続保存。7日より前の生履歴も削除しない。SQLiteは直近7日用の作業索引であり、永続生アーカイブの代わりではない。
- 旧 `trophy-battle-events-v1.json` は初回移行元のみ。以降の最新データはSQLiteと生アーカイブを使う。旧JSONの更新は停止する。
- 初回は既存の保存ランを順次読み直す。処理済みのオブジェクト名とETagを保存し、中断後も重複なく再開する。対象期間の全保存ランを処理するまで `coverage.state=backfilling`、完了後は `complete`。世界の全試合を網羅した意味ではない。
- 通常は1回4分を再読込作業の目安とし、次回へ持ち越す。これは実行時間の分割で、試合を切り捨てる上限ではない。手動の `collect.yml` に `rebuild_trophy=true` を渡すと20分を目安に保存済みデータのみを再集計する（ゲームAPI呼び出しなし）。通常収集と同じconcurrency groupで直列実行する。
- ジョブ上限は通常・保守とも45分。取得後の全件走査・圧縮・保存に時間を確保する。保存履歴の入力処理は通常4分・保守20分で分割し、新規API取得の速度・件数や毎時スケジュールは増やさない。
- Actionsは `tools/run-collector.sh` で収集・原本保存を完了させてから、新しいNodeプロセスで帯別全件集計を行う。前段の大きな分析用メモリを解放し、全件走査中の負荷を抑える。収集が失敗した場合は次段へ進まない。次段が失敗しても原本は保存済みで、次回再開できる。
- 公開JSONの `count` は重複除去後の試合数、`coverage.windowStart/windowEnd` は対象時間。少数帯の公開最低件数30件は維持するが、非公開集計には少数帯も残す。
- 秘密値を取り出さず、既存ActionsのR2認証を利用する。SQLite/生ログをGitや公開成果物へ含めない。

## 取得の配分と監視

- 一般候補8,000タグ／回、同時40件・間隔300msの予算は維持。APIの最大許容量と断定しない。
- 300トロフィー刻みで候補を選ぶ。最近の活動状況に応じた再訪を優先し、長く確認していない対象を探索する枠も残す。50,000候補の保持も帯別に配分し、人口の多い帯だけで静かな帯を押し出さない。
- `lastFetch` は選出したリスト全体や無関係な配列の先頭ではなく、実際にリクエストしたチャンクだけを更新する。
- 今回選ばれなかった候補も処理済み時刻を保持し、巡回のたびに同じ古い25戦を再保存しない。候補台帳から外れた分だけ処理済み時刻を整理する。生アーカイブの保存に失敗した場合は、処理済み時刻を進めず次回へ残す。
- 429・通信失敗・5xxだけ再試行。20秒で通信を打ち切り、Retry-Afterには従う。全段階終了後に429と取得品質を記録する。
- `private/collection-quality-v1.json` に候補数、帯別選出・成功数、実HTTP呼出し数、失敗数、25戦ログ数、前回取得との重なりがない可能性を記録する。タグ自体は出力しない。
- 同記録の `fetch` と `rate` はTop1000＋一般候補のバトルログ取得経路が対象。候補発見のクランAPI等の呼出し総数ではなく、`possibleRollover` は前回成功時刻を持つ一般候補が対象。候補発見側も20秒の通信期限と、Retry-Afterの秒数・日時の両形式に対応し、指定待機時間を15秒へ切り詰めない。
- 直近25戦というAPIの制約がある。3分未満の試合もあるので、毎時取得を欠損ゼロの保証にしない。取りこぼし可能性は、実際の取得間隔・ログの最古時刻から判断する。
- `possibleRollover` の判定には前回成功時刻が必要。新指標の初回収集では比較の基準を作るので、0でも取りこぼしなしの根拠にはしない。

検証：`node --test tools/test-event-store.mjs`。UTF-8境界、期限、上限超過、両者重複、中断再開、保存失敗、表示用集計、巡回対象・候補保持を検査する。

## 原本と品質監視（2026-09-23追加）

- Top1000と一般候補から取得した**公式API応答全体**を `private/raw/api-battlelogs-v1/日付/実行ID/part-N.jsonl.gz` に保存。カード名へ変換する前のID・形態・未知フィールド、引分、他モードも残す。約16 MiBずつディスクで分割し圧縮、件数上限では切らない。
- 最後にSHA-256・圧縮サイズ・応答数・観測数・コード/カード台帳の版を記したmanifestを保存する。`complete`はそのmanifest配下の全chunk保存完了を意味し、世界全試合取得や集計完了ではない。失敗時は処理済み位置を進めない。解釈中の例外でも受信済みバッチはfinallyで原本保存を試す。プロセス強制終了前の未アップロード分の保証はない。
- `read-battle-journal.cjs` はchunkのサイズ・SHA-256・最後の件数一致を検証して順次読み出す。下流の公開は走査成功後に行う。未知の意味を自動で解決する再分析器ではない。原本の再解釈は非公開分析側で実施する。
- 従来のlite原本も重い分析より先に保存する。双方のログに同一試合があればタグ対・日時のIDで重複排除。登録/課金対象の別経路も `registered-battlelogs-v1` に受信原本を残してから個人履歴へ反映。収集対象の課金条件は変更しない。
- 取得品質は `collection-quality-v1.json` のversion 2。帯は**要求時の候補帯**に固定し、再取得時の移動で成功率の分母がずれないようにする。Top1000は別グループ。HTTP試行状態、成功/失敗、25戦満杯、前回成功ありの比較母数、押し出し疑い、新規ログ観測、時刻/タグの欠損を記録。新規ログ観測は世界全体・サイト全体のユニーク増分ではない。旧形式の未取得指標は0と扱わない。
- 品質記録は `raw/collection-quality-v2/` に実行ごとの履歴も保存。SQLite全件走査の同じ過程で `collection/window-v1.json` に7日/24時間/UTC日別/帯別のユニーク件数と最終試合時刻を記録。公開側の最低表示標本条件を適用する前の件数で、既存の7日集計と合計が一致する。
- 品質診断はPRIVATE分析repo＋既存Workerの5分Cron。R2 `collection/plan-v1.json` の新鮮な配分表だけをcollectorが使用。20%を均等探索、残りは期限が来た候補を重み付きで取得。表が無い/3時間で失効した場合は均等配分。直近25戦の時間幅が短い人は期限を早め、同一帯では期限超過の割合を優先する。1時間未満の巡回は保証しない。
- 管理画面には7日/24時間件数・不足候補・原本保存・比較母数・保留件数を表示。診断と比較結果は管理者認証の後にだけ返す。
- 本番検証時の `collect.yml` 入力 `quiet_verification=true` は本番収集・保存を実行するが、その回の外部通知と後続の自動修理ジョブを止める。`data-test`でもR2本番保存先は変わらないため、隔離環境とは呼ばない。
